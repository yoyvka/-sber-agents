# Отчёт о выполнении задания: RAG-ассистент Сбербанка

## Название проекта и описание

**RAG-ассистент Сбербанка** — Telegram-бот с технологией RAG (Retrieval-Augmented Generation) для ответов на вопросы по банковским документам. Бот использует LangChain для индексации PDF-документов и JSON-датасета с вопросами-ответами, обеспечивая точные ответы на основе реальных документов Сбербанка о кредитах, вкладах и других банковских продуктах.

## Вариант задания

**Расширенный вариант** — реализована поддержка как PDF-документов, так и JSON-датасета с вопросами-ответами, проведены эксперименты с различными параметрами индексации и сравнение моделей эмбеддингов.

## Реализованные возможности

- [x] **RAG на базе LangChain** — ответы на основе реальных документов

## 🔬 Эксперименты с индексацией

### Описание экспериментов

Проведены эксперименты с различными параметрами разбиения документов для оптимизации качества поиска релевантной информации в банковских документах.

### Параметры, которые пробовали

#### Эксперимент 1: Базовые параметры
- **chunk_size**: 1500 символов
- **chunk_overlap**: 150 символов
- **separators**: стандартные (по умолчанию в RecursiveCharacterTextSplitter)
- **Результат**: 377 чанков из 2 PDF-документов

#### Эксперимент 2: Оптимизированные параметры для банковских документов
- **chunk_size**: 800 символов
- **chunk_overlap**: 100 символов
- **separators**: 
  - `"\n\n\n"` — тройной перенос (разделы)
  - `"\n\n"` — двойной перенос (параграфы)
  - `"\n"` — одинарный перенос
  - `". "` — конец предложения
  - `" "` — пробелы
  - `""` — символы
- **keep_separator**: `True` (сохранение разделителей для контекста)
- **Результат**: 246 чанков из 2 PDF-документов

### Наблюдения и выводы

**Проблема с большими чанками (1500 символов):**
- Чанки были слишком большими и содержали смешанную информацию
- Поиск возвращал менее релевантные результаты
- Контекст был избыточным для конкретных вопросов

**Преимущества меньших чанков (800 символов) с умными сепараторами:**
- ✅ Более точное соответствие запросам — чанки содержат более сфокусированную информацию
- ✅ Лучшее сохранение структуры документов — сепараторы помогают разбивать по логическим блокам
- ✅ Улучшенная релевантность поиска — retriever находит более точные фрагменты
- ✅ Оптимальный баланс между размером и контекстом — 800 символов достаточно для понимания, но не избыточно

**Вывод:** Для банковских документов оптимальной оказалась стратегия с **chunk_size=800**, **chunk_overlap=100** и кастомными сепараторами, учитывающими структуру документов (разделы, параграфы, предложения).

## 📊 Работа с JSON датасетом

### Реализация загрузки JSON

Для работы с JSON-датасетом использован **JSONLoader** из `langchain-community` с jq-схемой для извлечения данных:

```python
def load_json_documents(json_file_path: str) -> list:
    """
    Загрузка документов из JSON файла с вопросами-ответами
    Каждая пара Q&A становится отдельным чанком
    """
    loader = JSONLoader(
        file_path=str(json_path),
        jq_schema='.[].full_text',  # Извлекаем full_text из каждого элемента
        text_content=False
    )
    documents = loader.load()
    return documents
```

**Особенности реализации:**
- Использована jq-схема `'.[].full_text'` для извлечения поля `full_text` из каждого элемента массива
- Каждая пара вопрос-ответ становится отдельным документом (чанком)
- JSON-документы объединяются с PDF-чанками в единое векторное хранилище
- Результат: 212 пар вопрос-ответ из JSON + 246 чанков из PDF = **458 документов** в векторном хранилище
